# Comparative review — upstream PR #2613, the bgfx branch, and W3DNext

*2026-08-06 · requested by bobtista ("What does his branch have that mine is missing? vice versa? What does this branch get wrong? Where are we using the wrong approach?") · produced with the same multi-agent adversarial-review process used for W3DNext's own public audit (`v0.1.1`). Findings are evidence-anchored (file:line); claims that couldn't be verified by running the code are marked **unverified**.*

**Scope read:** [PR #2613](https://github.com/TheSuperHackers/GeneralsGameCode/pull/2613) full diff (752 lines, 7 files); [`bobtista/topic/trunk`](https://github.com/bobtista/GeneralsGameCode/tree/bobtista/topic/trunk) backend layer (IRenderBackend.h 1,281 lines and BgfxBackend.h read fully; BgfxBackend.cpp ~14.8k lines sampled at init/threading/submit/state-resolve; FixedFunctionState.h, cmake, A/B scripts, docs); W3DNext's backend (IRenderBackend.h fully, D3D11Backend* key sections, mirror hooks, parity tooling).

**Framing fact:** PR #2613 is a deliberately tiny first slice (157-line interface + pure-forwarding DX8Backend, zero behavior change) carved out of a much larger *shipping* bgfx branch — a working cross-platform port with rolling Windows/macOS-Metal/Linux-Vulkan releases, an SDL3 platform layer, and its own A/B tooling. Treat the PR as the merge vehicle and the branch as the destination. Also relevant: W3DNext's interface **deliberately mirrors PR #2613's shape** (our `IRenderBackend.h:19-23` says so in a comment) — these projects are convergent by design, not rivals.

---

## 1. What the PR + bgfx branch have that W3DNext is missing

1. **A backend-owned boundary instead of a mirror behind a live DX8 device.** On bgfx builds `dx8wrapper.cpp` is *not compiled at all* (branch `WW3D2/CMakeLists.txt:263-277`; `BgfxBackend.h:483-485`). The backend is authoritative. W3DNext keeps DX8Wrapper's state machine load-bearing in D3D11 mode (`D3D11Backend_W3D.cpp:485-490` mirrors state *back* into DX8Wrapper; seven `RB_Mirror_*` side-channel hooks in `dx8wrapper.h:149-186`). His escape hatches *cannot exist*; ours can and did (the raw-lock wave bug).
2. **Free multi-API + cross-platform via bgfx** — Metal/Vulkan/DX11 from one backend, one shader source compiled to all targets (`cmake/render-backend.cmake:8`, `CMakeLists.txt:306-332`). W3DNext is native-D3D11, Windows-only, single-GPU tested.
3. **Write-time buffer capture — the architecturally correct upload model.** Hooks the *unlock* moment (`Upload_Vertex_Buffer_Data` / `Capture_Dynamic_Vertex_Data`, branch `IRenderBackend.h:728-756`; sub-range updates at 775-788). W3DNext captures at *bind* time by re-locking (`D3D11Backend_W3D.cpp:463-491`) — re-uploads whole VBs per bind (our perf hole) and structurally cannot see writes that bypass the wrapper.
4. **Threading actually exercised:** bgfx render thread on by default with measured wins (+27% on a save, 24.75→31.56 fps Windows DX11, "validated pixel-identical", `BgfxBackend.cpp:504-524`). W3DNext is single-threaded.
5. **Resource lifetime designed for in-flight frames:** deferred-destruction queues with an explicit ABA analysis in the interface contract (`Release_Cached_Texture`, branch `IRenderBackend.h:540-546`), plus an opaque-handle asset-ingress layer (`RenderResource`/`Create_Texture`/`Create_Vertex_Buffer`, 343-396, 1266-1273).
6. **A static escape-hatch auditor** (`scripts/cpp/audit_bgfx_dx8_dependencies.py`) — mechanized hunting of raw-DX8 dependencies. W3DNext finds them one parity failure at a time.
7. **The modernization ceiling already exploited:** CSM sun shadows + PCF, point-light shadows, rim/specular, soft particles, SSAO/bloom, instancing (`shaders/fs_uber.sc:26-107`, `vs_uber_instanced.sc`). Whatever one thinks of divergence (§3), the branch proves the interface can carry a remaster.

## 2. What W3DNext has that the PR + branch are missing

1. **Runtime backend selection in one binary → frame-matched A/B.** `-gfxBackend d3d11` flips at init (`Backend/RenderBackend.cpp:32-80`); default is byte-identical DX8. His is a configure-time choice — two builds, two processes. Our DX8-vs-D3D11 frame dumps are frame-matched by construction on a deterministic tick schedule (`dx8wrapper.cpp:1678-1684`, `tools/parity/README.md`); his `ab_compare.py` must statistically mask wall-clock animation divergence and carry per-scene accepted-difference baselines (`ab_compare.py:9-14`). (His masking design is genuinely clever — see §4.6 — but frame-matched capture is the stronger oracle when available.)
2. **Parity as the contract, not a baseline of accepted divergence.** W3DNext's goal is DX8-equivalence, measured (29.36 vs 29.38 fps; menus ~99.8% byte-identical), down to preserving ShaderClass's alpha-test LESSEQUAL inversion at the interface-comment level (`IRenderBackend.h:192-199`). The branch *deliberately* diverges: fog unimplemented (honestly documented, `BgfxBackend.h:109-115`), bump-envmap and point sprites dropped (105-119), shadows/rim/bloom added. For a fork that's the product; for upstream's 1.04-compatibility charter, the parity discipline is the missing piece. **Unverified** how far visual output drifts in practice.
3. **Negative-control oracle discipline.** Our diff oracle is proven against synthetic known-bad pairs before use (`tools/parity/README.md`); dedicated single-symptom oracles exist. No falsification step found in `ab_compare.py`/`diff_drawcalls.py` (absence claim — those two scripts checked).
4. **Minimal upstream-merge surface for Windows:** W3DNext touches WW3D2 + a handful of funnels; stock WinMain/input untouched. The branch rewrote the platform layer (SDL3*), touches 90 files, and patches bgfx itself — right ambition, much larger review burden (exactly why PR #2613 slices thin).
5. **GPU-timing self-profiling in the interface** (`Gpu_Profile_Marker`, our `IRenderBackend.h:273-281`). His has draw stats + RenderDoc trigger, no in-interface GPU timestamps (**unverified** whether BgfxBackend.cpp hides an equivalent).
6. **For the record:** the bgfx branch is *not* scaffolding — it renders, ships rolling releases on three platforms, and self-tests against saved games. The asymmetry that survives scrutiny is parity-contract vs modernization-contract, and merge-sized slices vs monolith fork — and the PR shows the second one already being solved.

## 3. What each gets wrong

### PR #2613 (the interface slice)

1. **16-bit draw parameters in a backend-neutral interface** (`Draw_Triangles(unsigned short start_index, unsigned short polygon_count, …)`). DX8-era limits; modern backends and merged/instanced paths want more. W3DNext hit this and widened to `unsigned int` (backends narrow as needed); his own branch's newer submit paths also take `unsigned int` (branch `IRenderBackend.h:825-842`). Cheap to fix now, painful after N backends implement it.
2. **`Get_Back_Buffer(...) -> SurfaceClass*`** leaks a D3D8-wrapping type through the interface — and his own branch already superseded it with `Get_Back_Buffer_Description`/`Capture_Back_Buffer_Image` (branch `IRenderBackend.h:627-628`). Reviewers should ask for the branch's version now.
3. **`Set_Vertex_Shader(unsigned long)` documented as opaque** — the value is a D3D8 FVF-or-handle DWORD; the opacity claim relocates D3D8 semantics without naming them. Acceptable transitional; deserves an honest comment.
4. **Lifecycle wiring fragile for real backends:** `Init_Render_Backend()` is re-entry-guarded but the `Initialize(...)` call after it is not (PR `dx8wrapper.cpp:398-399`) — a repeated `Do_Onetime_Device_Dependent_Inits` double-initializes any backend with a non-trivial `Initialize`. **Unverified** whether that path can fire twice in a session.
5. **No story yet for the escape hatches — the class of bug that bites.** The PR parks "D3D8-typed low-level methods … as DX8Backend-specific escape hatches." Fine for a zero-behavior slice, but both codebases' scars (our raw-lock wave path; his `Skip_Next_Bgfx_Submit`/shroud-capture shims) show these bypasses are where invisible-state bugs live. Landing the branch's audit script alongside, as a CI ratchet on the hatch count, would materially strengthen the series.

### The bgfx branch

1. **The interface violates its own portability contract:** header demands "C++98/VC6-compatible: no STL in signatures" (`IRenderBackend.h:515`) yet includes `<vector>`, puts `std::vector<std::uint8_t>` in `RenderBackendImage` (81) and passes it through virtuals (628, 912), plus `nullptr`/default member init/braced-init (657-660). Either the VC6 constraint is dead (delete the comment) or the header breaks it. **Unverified** against the retail-compat VC6 build.
2. **Interface bloat, some of it backend-branded:** ~150+ virtuals including `Skip_Next_Bgfx_Submit()` (a named backend in the neutral interface, 1141), `Set_Tree_Shader_Constants` (964), `Capture_Shroud_Texture` (1194), letterbox fairness policy (554-559). Every new backend answers ~150 questions, many of which are really "am I bgfx?". *Symmetric confession:* W3DNext has the same disease in a different skin — our `RB_Mirror_Terrain_FF_Pass`/`RB_Mirror_Tree_Sway` hooks are subsystem-shaped too; his shims live in the interface, ours beside it. His scales worse with backend count, ours with subsystem count. Neither is the final shape.
3. **"Neutral" enums pinned to D3D8 ABI values by design** — ten enum blocks documented as "values match legacy ordinals so DX8Backend can cast directly" (404-511), lock flags are literal `D3DLOCK_*` bits, texture ops literal `D3DTOP_*` ordinals. A documented cast-saving trick that makes D3D8's ABI the permanent wire format of the neutral layer. W3DNext chose the opposite (values deliberately match no native API) — one switch per backend buys real neutrality.
4. **Pointer-keyed transient caches — the ABA trap, hit once, still present elsewhere.** Textures were pointer-keyed until dangling aliases forced deferred destruction (540-546 documents the ABA); dynamic-buffer capture is still "keyed by the access class pointer" (748-750). W3DNext hit the identical bug and moved to never-recycled ids + generation counters (`D3D11Backend_W3D.cpp:784-795`). Same class of bug remains reachable (**inference from the header contract; unverified** whether the .cpp adds generations internally).
5. **A compatibility renderer it is not** (no fog, added shadows, per-scene accepted-divergence baselines). As the fork's product, fine; as upstream's only modern backend it would change the 1.04 look. The PR series' implied destination is a visually divergent renderer unless parity discipline is added separately.

### W3DNext (same rigor applied to ourselves)

1. **DX8-shaped interface by construction; the backend can't stand alone.** DX8Wrapper stays a live, load-bearing state machine that the D3D11 backend must feed (mirror-back at `D3D11Backend_W3D.cpp:485-490`; inbound `RB_Mirror_*` hooks). Dual bookkeeping is a standing divergence generator; `dx8wrapper.cpp` can never be deleted on this trajectory. His cut-the-cord model is the correct end-state; ours is defensible only as the parity-transition vehicle it was designed to be.
2. **Raw-D3D8-lock writes invisible to the mirror** (wave path) — known, open; oracle exists, root fix doesn't.
3. **Menu black-sprite artifact unlocalized** — an active hunt (the reviewed branch is literally `debug/menu-black-recorder`).
4. **Per-bind full-VB re-upload; no buffer cache.** The texture side got a cache after profiling convicted ~40 ms/frame of redundant upload; the VB side hasn't (menu 14–26 fps vs DX8's 30 cap). His static-buffer + sub-range-update model is the designed fix.
5. **WriteLock-as-read is fragile** — reading via a write lock, skipped on an engine-refs invariant argued only in a comment (`D3D11Backend_W3D.cpp:471-477`); the same shape of reasoning that hid the wave bug.
6. **Narrower FF emulation by scope** (6 combiner ops/4 stages vs his 17 ops/8 stages) — justified for ShaderClass's actual traffic, but every raw TSS poke outside the envelope becomes a bespoke mirror hook; the whack-a-mole is structural.
7. **Single-GPU, single-platform test surface; own docs drift** (parity README predates the `-gfxBackend` flag it says doesn't exist).

## 4. Wrong-approach judgment calls the contrast exposes

1. **Backend authority:** cut-the-cord (his) is right for the end-state; the mirror (ours) bought frame-matched A/B for the transition. Synthesis: runtime-selectable backends (ours) over a single authoritative state model (his) — move DX8Wrapper's record/apply into backend-neutral code once; his `FixedFunctionState` extraction is visibly heading there.
2. **FF emulation:** both sides independently chose the übershader + hashed-state-word design. Treat it as settled, twice validated; no permutation-cache work justified until profiling says so.
3. **Buffer updates:** write-time capture (his) beats bind-time relock (ours), full stop. Adopting his hook shape is W3DNext's single highest-value port — it fixes the wave-class invisibility *and* the per-bind upload cost at the root. (Honest limit: write-time capture still can't see raw-device locks; only removing the D3D8 device does.)
4. **Interface granularity:** the PR slice is the right grain; both grown interfaces are wrong in opposite directions (his 1,281-line header with subsystem/backend-named virtuals; our 293-line header that stays clean by exporting the mess into side-channel hooks). Landing-zone shape: PR core + his typed state groups (minus ABI pinning) + our widened counts and neutral values, with subsystem-specific virtuals quarantined in an extension interface.
5. **State enums:** neutral values (ours) over ABI-matched (his) — one switch per backend is the whole cost.
6. **Parity methodology:** frame-matched capture (ours) where possible; his animation-mask compare regardless — it mechanically catches the frozen-animation class of bug that single-frame diffs miss (a blind spot our own retro found independently). Each side should adopt the other's half.
7. **bgfx vs native D3D11:** different products, not wrong-vs-right. bgfx buys three platforms + a shader toolchain for the price of a patched third-party dependency and its constraints; native D3D11 buys exact control for parity on the platform with 100% of the retail audience. If cross-platform is upstream's goal (its README says it is), bgfx-behind-the-interface is the defensible default — and a native D3D11 backend is simply a second implementation of the same interface, which is exactly what the interface exists to permit.

## Strategic read

**PR #2613 is a good landing zone for a W3DNext-style D3D11 backend — with four amendments:** (1) widen the 16-bit draw counts to `unsigned int` (his own branch already did on newer methods); (2) neutral enum values, not D3D8 ordinals; (3) replace `Get_Back_Buffer -> SurfaceClass*` with the branch's own description/capture pair; (4) land the write-time buffer-upload hooks early in the series — both codebases' scars show bind-time capture is a dead end. With those, porting W3DNext onto the merged interface is days-not-weeks of mechanical alignment (our header already mirrors the PR's shape on purpose; ours is a superset-with-deltas: `Set_Alpha_Reference`, `Gpu_Profile_Marker`, dynamic staging, filter-quad, backbuffer capture).

The genuinely hard part isn't the interface — it's that upstream would host two backend philosophies (authoritative-backend bgfx vs mirror-transitional D3D11), and the mirror hooks have no home in his model. W3DNext would either carry its DX8Wrapper funnel edits as a Windows-only parity mode, or adopt cut-the-cord and lose same-binary A/B.

**Adoption list — bobtista from W3DNext:** runtime backend selection in one binary; deterministic frame-matched A/B; negative-control discipline for the diff oracles; parity-first sequencing for upstream (equivalence first, divergence behind flags); neutral enum values; id+generation resource keying everywhere, not just textures.

**Adoption list — W3DNext from bobtista:** write-time buffer capture + sub-range updates (top priority); the escape-hatch audit script as a ratcheting CI count; the animation-mask compare structure; the typed state-group setters; the `RenderResource` asset-ingress layer as the mirror's eventual replacement; and the end-state ambition — a backend that renders the game with `dx8wrapper.cpp` not even compiled.
